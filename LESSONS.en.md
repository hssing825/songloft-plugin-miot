### MIOT-006: Artist and playlist playback need external search after a local miss

- Scope: rule and AI execution of `play_artist` / `play_playlist`.
- Evidence: on 2026-10-15, [songloft-org/songloft#522](https://github.com/songloft-org/songloft/issues/522) reported that configured external sources were unused when local artist/playlist lookup missed. Baseline `05bb8133c0057ca7a06ff36f416f7d69833d17b9` returns immediately from both executors after a local miss. Current source already has failure TTS but lacks external fallback; the reported silence does not establish that all versions lack feedback.
- Fix: this change uses the parsed name as the external keyword when an artist has no local songs, its songs cannot be loaded, a named playlist misses/is empty, or the index is unavailable. Reuse `findExternalSongCandidate` / `playSongCandidate` without pretending the artist/playlist name is a song title hint or repeating prepare/stop. Local hits retain random artist queues/original playlists; empty arguments retain default-playlist and resume behavior.
- Done right: 22 of 37 new regressions fail for the intended behavior in an isolated baseline copy, and all pass after the fix. All 938 plugin tests, type checking, QuickJS build, and package validation pass. Tests use the real `OnlineSearcher` with fixture HTTP/device interfaces, asserting keywords, playback URLs after import, a single interruption, incremental indexing, no-import direct push, appended-playlist continuation, and failure TTS. They cover all three song-search priorities while retaining local-first artist/playlist behavior. Evidence: `/tmp/songloft-522-{baseline-isolated,tests,typecheck,build,validate}.log` and `/tmp/songloft-522-verification.json`.
- Rule: successful AI parameter extraction does not prove the executor supports external search. Verify each action's local-miss path and playback effects separately, rather than testing only `play_song` or the AI analysis endpoint. The topone fallback fetches one song candidate; it does not promise a complete external playlist or artist collection.
- Not run: the reporter's lxserver/Subsonic topone, physical speaker audio, deployed-plugin upgrade, and long-running acceptance. Host interfaces are unchanged; there are no Go backend changes.
- Seen 1× (2026-10-15). Status: lesson; verify deployment and physical-device acceptance separately.

### MIOT-005: Duration-mismatch protection must survive recovery timer rebuilds

- Scope: voice, resume verification, hourly recovery, and tail checks when metadata and device stream duration disagree.
- Evidence: the two logs in the [new songloft-org/songloft#495 report](https://github.com/songloft-org/songloft/issues/495#issuecomment-6167015011) on 2026-10-14 overlap and are not independent incidents. At 19:02:32 the original stream reached 611.5 seconds (metadata 571, device duration 928.318); voice was detected at 19:02:37, the same episode was repushed at `seek=567` at 19:03:08, and the replacement stream reset before advancing at 19:03:38. Recovery queries lack complete logged states, so this does not prove the cause of every audible jump.
- Reproduction: baseline `fb041740468f41f1f56b1b1f90082a75ab0f98fd` accepts continuous progress of a mismatched stream in deadline checks but classifies it as foreign during recovery using only metadata duration. Nine cross-path cases across three seek/speed combinations all fail against an isolated baseline through repush, incomplete recovery, or subsequent premature advancement. Rebuilding timers also loses progress beyond the metadata ±15-second initial evidence window.
- Fix: the fix retains the stream-duration signature confirmed by consecutive tail samples, bound to song/seek/speed, for recovery identity. Timer rebuilds may establish a new baseline on that stream but still require new advancing samples. Pause/voice suspension preserve the signature; repush, playlist replacement, stop, external takeover, and cleanup clear it. The signature is not an accurate duration; metadata and server seek guards remain unchanged.
- Done right: all 893 plugin tests, 64 frontend tests, type checks, QuickJS build, and package validation pass. Parent `CGO_ENABLED=0 make check`, playback/Range, and timer regressions pass. Nine cross-path cases assert continued playback beyond 30 seconds, actual next two URLs, no failure marks/TTS, and no timers after cleanup. Additional checks cover foreign duration, duplicate samples, query failures, and signature lifecycle. Evidence: `/tmp/songloft-495-20261014/`.
- Not run: physical LX05 playback, original problem audio, firmware version, installed server SHA, and long-running acceptance. Brief device looping before cloud confirmation can remain. Accurate seeking after lost media beyond metadata duration still requires original audio/server-duration verification; the entire issue is not declared resolved.
- Seen 1× (2026-10-14). Status: lesson; duration differences and physical transition behavior await acceptance.

### UI-001: Calibrate touch input and verify that samples are current

- Scope: mobile-sized plugin settings, Docker Chrome touch emulation, and native Android WebView.
- Rule: Do not treat missing automated scrolling as a page bug. First verify that identical input changes `scrollTop` in an ordinary overflowing control. Native checks must also confirm the foreground app, advancing sample timestamps, and increasing touch events. Discard old samples after a crash or navigation that did not enter the plugin. Distinguish desktop Chrome emulation, Android emulators, and the reporter's physical phone.
- Evidence: investigating [songloft-org/songloft#519](https://github.com/songloft-org/songloft/issues/519) on 2026-10-14, Docker Chrome 121.0.6167.85 kept `scrollTop=0` even in a normal control with `Input.synthesizeScrollGesture(gestureSourceType=touch)`; `Input.dispatchTouchEvent` moved that control to 265. The initial native Android 15 experimental 16KB image's WebView 124 crashed with SIGTRAP in `libmonochrome_64.so` on `MemoryInfra`; non-scrolling samples after app exit were discarded. Retesting on a standard 4KB image recorded no crash. The crash root cause remains unproven and is not established as the reporter's #519.
- Done right: isolate `db4bd0c2fc5ad55a7a557743fe691480f300ce28` (v2026.10.14) for browser controls, then install the SHA-256-verified official Android 2.13.1 x86_64 APK and official 2.13.0 lite backend. Final checks use unchanged JS/CSS from the official October 14 plugin release; only HTML adds passive telemetry, with fixture device/song APIs. Android 15 / WebView 124.0.6367.219 / 4KB passed all six categories in both the bottom Tab and standalone home entry (12 scroll checks), two Tab/app lifecycle checks, and a reduced-height menu scrolling from 0 to 184. JSON evidence and screenshots: `/tmp/songloft-519-android-2131/`, consolidated in `report.json`. No functional source changes; existing worktree changes are preserved.
- Not run: the reporter's physical phone, ARM APK runtime, and actual device/cloud configuration. The follow-up identified Redmi Note 9/Note 7, Android 12, WebView 103.0.5060.129, the bottom smart-speaker entry, and scrolling within categories. Non-reproduction on WebView 124 is not an issue fix and does not establish a link to Windows #499.
- Seen 1× (2026-10-14). Status: lesson; see UI-002 for subsequent evidence on older-engine height fallback. The reporter's physical phones still await retesting.

### UI-002: New units combined with variables can invalidate older-browser fallbacks

- Scope: definite heights in MIoT settings, older Chromium/WebView engines, and safe-area layout.
- Rule: A `vh` declaration before `calc(100dvh - ... - var(...))` does not guarantee compatibility. A declaration containing `var()` may discover an unsupported unit only at computed-value time, when earlier declarations are no longer reconsidered. Prefer the parent's definite content height; isolate new units combined with variables using `@supports` when necessary, and verify height and touch scrolling in an actual older engine.
- Evidence: on 2026-10-14, the [songloft-org/songloft#519 follow-up](https://github.com/songloft-org/songloft/issues/519#issuecomment-6170532402) identified category scrolling failures on Android 12 / WebView 103; the video shows Playback and Devices. Previous fix `c4d5a80066ee51c4c694fb6d7a4ae01774499f37` only added `vh` fallbacks. An isolated build of baseline `566dea7bd1cd2ee78ca46131933d603b52337d1b` on Docker Chromium 103.0.5058.0 / 104.0.5109.0 expanded Devices with additional long content to 3059px in a 390×640 viewport, with `scrollTop=0` before and after touch. The same input scrolled an ordinary control correctly, and a newer browser worked.
- Fix: the uncommitted worktree changes `.settings-scroll-body` to `height: 100%`, inheriting the parent's content height after app-bar and safe-area padding. The parent's variable-free `100vh` / `100dvh` declarations still fall back correctly. Added `frontend/tests/settings_scroll.browser.cjs` to calibrate touch, verify the actual category, and check viewport bounds and `scrollTop`.
- Done right: Chromium 103.0.5058.0 / 104.0.5109.0 / 121.0.6167.85 each passed six categories × three screen sizes (18 checks), including a 24px top safe area. The older engine's Devices viewport returned to 584px, and touch moved `scrollTop` to 225. All 901 plugin tests, 64 frontend tests, both type checks, QuickJS build, and package validation passed. Layout checks use mock APIs and additional long content; all three engines verified the same complete plugin package. Logs, JSON, and screenshots: `/tmp/songloft-519-followup/`.
- Not run: physical Redmi Note 9/Note 7, native Android 12 WebView 103.0.5060.129, and actual account/speaker configuration. Desktop older-engine reproduction and fix verification do not establish acceptance on the reporter's phones.
- Seen 1× (2026-10-14). Status: lesson; source fix verified locally, publication and physical-device retesting pending.

### MIOT-004: Disabling context must govern both request content and background generation

- Scope: AI chat history, summaries, preference memory, and configuration migration.
- Evidence: on 2026-10-14, [songloft-org/songloft-plugin-miot#119](https://github.com/songloft-org/songloft-plugin-miot/issues/119#issuecomment-6162510329) asked whether disabling memory still sends history. At baseline `db4bd0c2fc5ad55a7a557743fe691480f300ce28`, the memory switch does not govern history/summaries, and background summaries have no independent switch. Reducing recent turns does not bound the older summary.
- Rule: Define local retention, conversation context, and preferences independently. With history off, neither inject nor generate summaries; with preferences off, neither extract nor inject memories. Keep inexpensive new defaults separate from legacy migration to avoid silently changing existing behavior.
- Done right: five context regressions in this change fail for the expected behavior on an isolated old implementation and pass after the changes. Actual Songloft/QuickJS, the built plugin, and Docker Chrome verify that both context sources off sends only the role prompt/current question, and SSE partial text displays and survives cancellation. Evidence: `/tmp/songloft-119-sse/`. Mock models and fictitious devices do not establish native TTS audio.
- Seen 1× (2026-10-14). Status: lesson; semantics in [AI chat](docs/en/ai-chat.md).

### MIOT-003: A recovery task can outlive the timer that started it

- Scope: voice recovery tasks, hourly recovery, and timer compatibility with older hosts.
- Additional same-day evidence: in the [22:01 logs for songloft-org/songloft#495](https://github.com/songloft-org/songloft/issues/495#issuecomment-6170232077), episode 136, White Horse Alliance (songId=10598), registers a 552000ms timer at 19:03:40.882, due at 19:12:52.882. No `Timer fired` or automatic completion appears before a manual next-track action at 21:15:25.393. The same song has 39 playback requests in 13 read cycles roughly 622 seconds apart; individual 206 requests must not each be counted as a replay. The logs contain no timer IDs, installed-package SHA, or version changes. Timer loss is an investigation lead, not proof that an old recovery task deleted it.
- Follow-up and delivery: the reporter subsequently [confirmed they had not upgraded to v2026.10.15](https://github.com/songloft-org/songloft/issues/495#issuecomment-6170461107), supplied the audio source, and reported an invalid-token error when stopping. With user confirmation, the [reply was posted and read back](https://github.com/songloft-org/songloft/issues/495#issuecomment-6170546561), requesting an upgrade to plugin v2026.10.15.2 before retesting continuous playback, voice recovery, and automatic advancement. The token error is recorded separately and the issue remains open. A reported version does not verify the installed-package SHA; this loop is not declared fixed.
- Additional validation: 439 playback regressions pass at plugin `4556287e4ccac365cc06af580c21ce6d222a96f6`; Go Timer regressions pass at parent `bf1612be90ac83809f57aad963587a4ec5944456`. An isolated copy with only voice recovery replaced by the `1cb1b52` implementation fails the existing recycled-handle regression because the next URL is not sent; the current implementation passes. This proves that code defect and its existing fix, not the reporter's installed fix or the cause of this loop. Evidence is in `/tmp/songloft-495-loop-20261014/`; installed-version verification, the physical device, and original audio are `Not run`. This same-day investigation does not increase Seen.
- Feedback: [latest songloft-org/songloft#481 comment](https://github.com/songloft-org/songloft/issues/481#issuecomment-6160171475), 2026-10-14: long recovery waits and tracks ending without advancing. The log creates hourly recovery at 11:00:47.820, sends bare play at 11:00:59.323, and repushes only at 11:01:04.319 after status=0. A next-track timer registered at 10:06:44.505 has no firing entry. The log has neither a backend SHA nor timer IDs, so that missing timer cannot be conclusively attributed to handle reuse.
- Reproduction: at baseline `0ba32df6314542856dfc4f9253400f59e373acc6`, a started voice task retains its expired timeout handle. Using the timer-reuse semantics of released host v2.13.1, cancelling the recovered task deletes a transition timer that reused the same ID; the new regression fails on the isolated old implementation because the next-track URL is never sent. Host [32ff4ca](https://github.com/songloft-org/songloft/commit/32ff4ca8002d898fdf79012772610e2c8e45f3f1) fixes global handle reuse but is absent from v2.13.1; updating only the plugin does not update the host.
- Fix: this change clears the handle immediately in its callback, retaining task identity for background verification and cancellation. After consecutive fresh idle confirmations, voice/hourly recovery directly repushes a safe seek URL when status=0/3 has neither position nor stream duration, avoiding ineffective bare play and another verification round. Media-bearing or paused states retain resume verification. Hourly recovery allows at most four fast queries plus one late idle confirmation; a failed query immediately restores normal spacing rather than continuously bypassing backoff.
- Done right: all ten new cases fail for the intended behavior on the isolated old implementation. The fix passes all 862 plugin tests, 62 frontend tests, type checks, build/package validation, and parent `make check`. Coverage includes actual URLs for two consecutive natural transitions after cancellation on a recycling host, missing media, the shared five-second cache, half-second cloud responses, speech waiting, and failure backoff. Simulated repush completes three seconds after voice scheduling or two seconds after hourly task creation with two half-second responses; this excludes conversation discovery, interruption detection, and real device buffering, and is not a promise of matching device latency.
- Not run: audible L15A playback, original problem tracks, and long-running acceptance; the reporter's backend version still needs confirmation. The existing twenty-second background interruption-detection cadence remains; this change shortens recovery after interruption has been confirmed.
- Seen 1× (2026-10-14). Status: lesson; see the device regression matrix in [AGENTS.en.md](AGENTS.en.md).

### MIOT-002: Report asynchronous submission and subsequent page refresh separately

- Scope: AI chat tests and other page actions that refresh history after submission.
- Feedback: [songloft-org/songloft-plugin-miot#119](https://github.com/songloft-org/songloft-plugin-miot/issues/119#issuecomment-6158362927), 2026-10-14: the page reported failure while the speaker read the answer. No specific error was supplied, so the reported root cause remains unconfirmed.
- Reproduction and fix: the page at baseline `adace3586ed187555da5831e9d3926a0521403bb` handled `POST /chat/messages` and subsequent history refresh through one error path. With successful submission and a failed history read, the new test failed on the old implementation's error feedback. The current uncommitted worktree separates history warnings from submission/task errors and prevents stale refresh warnings from affecting a new device or newer refresh.
- Done right: frontend tests cover successful feedback for accepted questions, separate history warnings, and stale-error rejection. Docker Chrome used a 202 acceptance and simulated history 500 to verify the cleared question, absence of submission errors, and eventual answer in history; a test-service readback confirmed completion. The browser fixture is independent of the speaker cloud and does not establish the reporter's exact failure path or audible device speech.
- Seen 1× (2026-10-14). Status: lesson.

### MIOT-001: Distinguish successful idle samples from query failures when tail progress disappears

- Scope: automatic transitions on devices whose stream duration differs from song metadata.
- Failure: [latest feedback on songloft-org/songloft#495](https://github.com/songloft-org/songloft/issues/495#issuecomment-6144580047), 2026-10-13. The earlier fix [4aeadc5](https://github.com/songloft-org/songloft-plugin-miot/commit/4aeadc559a04c5ddf329277425e4df3660d17f8a) protected continuously advancing playback, but the device removed `play_song_detail` at natural completion. Successful idle responses were treated as missing progress alone. Logs repeatedly reported `status=0, hasPosition=false, duration=0` from 19:28:01 to 19:28:25; transition waited for grace expiry, leaving silence.
- Fix: uncommitted worktree based on `587b77f000d7af4b022229b293bc519b3a957851`. Only after confirming continuous progress of the current stream into the metadata tail does `observeDeadlineTail` accept two fresh successful idle samples without position/duration as completion evidence. A fallback zero is still not a real position reset; query failures, foreign durations, and buffering while playing retain bounded grace.
- Done right: `player_transition` covers idle 0/2/3, seek/speed, single misreports, repeated cache, query failures, resumed progress, and foreign durations. `player_failures` uses the logged 593/651-second durations and asserts actual next URLs, natural completion of two successive episodes, failure markers, TTS, and subsequent timers. All 16 new completion scenarios failed for delayed transitions against an isolated old implementation; all 840 tests pass with the fix. Real-speaker listening was not run; simulated clocks do not prove seamless audio.
- Duration boundary: this log shows 651 seconds in metadata and 723.289 seconds for the device stream, while position still advances to 732 seconds. Neither duration alone proves completion or justifies writing device duration into song metadata. Actual source differences still require the real device/original audio to verify.
- Seen 1× (2026-10-13). Status: lesson; existing regression requirements remain in the transition matrix in [AGENTS.en.md](AGENTS.en.md).
